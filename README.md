# ember — лабораторні роботи

Лабораторні 1–4 з основ програмування. Розділи розташовані за номером роботи.

## Лаба 1 — Коробка байтів

Взяв скелет ember і дописав читання та запис байта, ASCII-колонку,
вивід байта у чотирьох форматах і команду `inc`.
Робив у GitHub Codespaces на Linux, компілятор GCC 13.3.0.

## Як запустити

    cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug
    cmake --build build
    ./build/ember

Збирав на C++17 з `-Wall -Wextra -Werror`. У Debug увімкнені ASan і UBSan.

Команди: `dump`, `get <addr>`, `set <addr> <value>`,
`inc <addr>`, `help`, `quit`. Адреси — від 0 до 4095, значення — від 0 до 255.

## Розміри типів

Перевірив через `sizeof`:

| Тип | Байтів |
|---|---|
| char | 1 |
| uint8_t | 1 |
| uint16_t | 2 |
| int | 4 |
| unsigned | 4 |
| float | 4 |
| double | 8 |


Для комірки використовується `std::uint8_t`: це один байт, який зберігає
0–255. `int` у моєму середовищі займає чотири байти.

## Перевірка пам’яті

Після нового запуску виконав `dump`. Пам’ять заповнена нулями завдяки
`Byte data[MEM_SIZE]{}`. Ось вітання і перші три рядки:

```text
ember 0.1 - 4096 bytes of memory you can see. Type `help`.
ember> 0000  00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00  |................|
0010  00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00  |................|
0020  00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00  |................|
```

Записав 255, перевірив через `get 0`, виконав `inc 0` і знову `get 0`.
Отримав 0: при перетворенні числа 256 у байт воно загортається за модулем 256.
Команда `inc 5000` дала помилку, бо такої адреси немає.

Потім виконав `set 0 65`, `get 0`, `set 1 66`, `set 2 0` та `dump`:

```text
ember 0.1 - 4096 bytes of memory you can see. Type `help`.
ember> ember> 255  0xff  0b11111111  '.'
ember> ember> 0  0x00  0b00000000  '.'
ember> address is outside 0..4095
ember> ember> 65  0x41  0b01000001  'A'
ember> ember> ember> 0000  41 42 00 00 00 00 00 00 00 00 00 00 00 00 00 00  |AB..............|
0010  00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00  |................|
0020  00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00  |................|
```

65, 0x41, 0b01000001 та A — той самий байт у різних форматах.
У дампі видно AB. Нуль після букв завершує C-рядок, а в ASCII-колонці
показується крапкою. Кілька `ember>` підряд у файлі з’явилися через подачу
команд через стандартний ввід.

## Переповнення int

В окремій програмі взяв найбільше значення `int` і додав 1.
Зібрав із `-fsanitize=address,undefined -fno-sanitize-recover=undefined`.

```text
Before: 2147483647
/tmp/lab01-overflow.cpp:7:11: runtime error: signed integer overflow: 2147483647 + 1 cannot be represented in type 'int'
```

UBSan повідомив про переповнення і зупинив програму.
Для знакового `int` це невизначена поведінка. Очікувати загортання,
як у беззнакового байта, не можна.

## Дроби

Порівняв `0.1 + 0.2` з `0.3` і надрукував 17 значущих цифр:

```text
0.1 + 0.2 = 0.30000000000000004
0.3       = 0.29999999999999999
equal: false
```

Отримав `false`. Ці дроби зберігаються в `double` приблизно, бо не мають
точного скінченного запису у двійковій системі. У виводі видно невелику
різницю, а `==` перевіряє точну рівність.

## Що буде без {}

Зробив копію проєкту, прибрав `{}` з масиву і запустив `dump`.
У `main.cpp` об’єкт створювався як `Memory mem;`.

```text
ember 0.1 - 4096 bytes of memory you can see. Type `help`.
ember> 0000  00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00  |................|
0010  00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00  |................|
0020  00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00  |................|
```

На початку дампа все одно побачив нулі. Але без ініціалізації вони
не гарантовані, а читання такої пам’яті у C++17 — невизначена поведінка.
ASan і UBSan не зобов’язані її помітити. В основному проєкті `{}` залишив.

## Лаба 2 — біти й маленький CPU

У цій лабі додав процесор з регістрами A, B, PC і прапорцями Z, N, C. Команди вводяться в тому ж REPL.

Працюють такі інструкції: HALT, NOP, ADD, SUB, AND, OR, XOR, NOT, SHL, SHR, INC, DEC. Опкод ділю на групу та номер через (op >> 4) & 0x0F.

### Коротка перевірка

200 + 100 у байті дає 44, бо 300 не вміщується в 8 біт. Після ADD маємо A=44 і C=1.

    reg a 200
    reg b 100
    set 0 16
    step
    regs
    PC=1 A=44 B=100 Z=0 N=0 C=1

Ще приклад зі зсувом: якщо в A лежить 128, команда SHL дасть A=0, Z=1, C=1: старший біт вийшов назовні.

Трасування програми з трьох інструкцій:

    set 0 16   # ADD
    set 1 24   # INC
    set 2 0    # HALT
    reg a 200
    reg b 100
    step       # A=44, C=1
    step       # A=45, C лишається 1
    step       # CPU halted


## Лаба 03 — адреси та пам’ять

Додав 16-бітний доступ, інструкції 0x20–0x2C, OUT (0x02), OUTN (0x03) і run.
PC рухається на довжину інструкції: 1, 2 або 3 байти. H тримає адресу, A і B — значення.
Нові інструкції не змінюють Z, N, C. run зупиняється на HALT або помилці.

Збірка та перевірка:

```sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug
cmake --build build
./build/ember < checks/lab-03.txt
./build/ember < checks/lab-03-h.txt
c++ -std=c++17 -Wall -Wextra -Werror -g -fsanitize=address,undefined -Isrc checks/lab-03-test.cpp src/cpu.cpp src/alu.cpp src/memory.cpp -o /tmp/lab03-test
/tmp/lab03-test
```

Тести перевіряють усі нові опкоди, довжини інструкцій, незмінність прапорців,
останню допустиму пару байтів і відмову при виході за пам’ять. Результат: LAB03 TESTS PASSED.

### Порядок байтів

set16 записує молодший байт першим: для 0x1234 це 34 12. get16 збирає їх назад: lo | (hi << 8).
Команди get16/set16 приймають адреси 0..4094. При set16 4095 запису немає, бо другого байта вже не існує.
У перевірці число лежить на 0x10, щоб не заважати програмі:

```text
set16 16 0x1234
get16 16
4660
0010  34 12 00 00 00 00 00 00 00 00 00 00 00 00 00 00
```

### Код і дані

Програма починається з 0x000, повідомлення — з 0x800.
Абсолютна адреса 0x0800 у коді займає байти 00 08:

```text
0000  22 00 08 02 00 00 00 00 00 00 00 00 00 00 00 00
0800  41 42 43 00 00 00 00 00 00 00 00 00 00 00 00 00
ember> Aember> PC=5 H=0 A=65 B=0 Z=0 N=0 C=0
```

LOAD читає 65 з 0x800, OUT друкує A, HALT зупиняє виконання.
OUT не додає нового рядка, тому запрошення ember> стоїть відразу після літери.
Повний дамп і вивід збережені у [checks/lab-03-output.txt](checks/lab-03-output.txt).

Другий варіант використовує H. Код: 28 00 08 29 02 2b 29 02 00.

| Інструкція | PC після кроку | H | A | Вивід |
|---|---:|---:|---:|---|
| LOADH H, 0x0800 | 3 | 2048 | 0 | |
| LOAD A, [H] | 4 | 2048 | 65 | |
| OUT | 5 | 2048 | 65 | A |
| INCH | 6 | 2049 | 65 | |
| LOAD A, [H] | 7 | 2049 | 66 | |
| OUT | 8 | 2049 | 66 | B |
| HALT | 9 | 2049 | 66 | |

У [трасуванні](checks/lab-03-h-output.txt) після кожного step є regs. Повторний step після HALT друкує halted.
INCH пересуває H на один байт. У C++ це відповідає ++p для Byte*, а для int* крок був би sizeof(int) байтів.

### Вказівник хоста і адреса гостя

Memory* у CPU вказує на об’єкт пам’яті в нашій програмі C++. PC і H — числа всередині ember:
наприклад, H=2048 означає комірку data[2048]. Це не адреса оперативної пам’яті комп’ютера.
Якщо записати справжній Byte* у 16-бітний регістр, частина адреси загубиться; до того ж після
нового запуску адреса об’єкта може змінитися. Тому спочатку перевіряємо індекс гостя, потім звертаємось до масиву.

### Дослід з ASan

Окремий [приклад](checks/lab-03-asan.cpp) навмисно записує data[4096] при розмірі 4096.
Він не входить до збірки ember. Запуск:

```sh
c++ -std=c++17 -Wall -Wextra -Werror -g -fsanitize=address checks/lab-03-asan.cpp -o /tmp/lab03-asan
/tmp/lab03-asan
```

З отриманого звіту:

```text
ERROR: AddressSanitizer: stack-buffer-overflow
WRITE of size 1
#0 ... in main checks/lab-03-asan.cpp:6
[32, 4128) data (line 4) <== Memory access at offset 4128 overflows this variable
```

Це запис одного байта одразу після масиву, рядок 6. Повний [звіт ASan](checks/lab-03-asan.txt) збережено.
В ember такого прямого запису немає: mem_set перевіряє межу, set16 перевіряє місце для двох байтів,
step перевіряє PC, операнди та адресу даних до виконання. Виправлення для досліду — відхилити index >= 4096 до запису.

## Лаба 4 — умови та цикли

У step тепер один switch з окремими case для опкодів. Невідома команда
друкує, наприклад, unknown opcode 0xff і зупиняє CPU на адресі помилки.
Додав CMP (1A), JMP (30), JZ (31), JNZ (32) і HLOW (2D) з ISA.
CMP виставляє Z/N/C як A-B, але не змінює A і B. C означає позику: A < B.
LOADI прапорці не змінює, тому для порівняння потрібен CMP.

run виконує не більше 100000 інструкцій за один виклик. Якщо HALT не зустрівся,
друкується step limit reached (100000). Стан CPU залишається для regs/step;
це зупинка запуску, а не HALT. Повторний run може продовжити виконання.

### Зворотний відлік

Адреси та байти нижче записані в hex:

```text
адреса  байти     інструкція
0000    20 03     LOADI A, 3
0002    03        OUTN
0003    19        DEC A
0004    32 02 00  JNZ 0002
0007    00        HALT
```

```sh
./build/ember < checks/lab-04.txt
```

Вивід: 3 2 1. Наприкінці PC=8, A=0, Z=1.
Нижче стан після кожної інструкції (PC у десятковій системі):

| Крок | Виконано | PC | A | Z | Вивід |
|---:|---|---:|---:|---:|---|
| 0 | старт | 0 | 0 | 0 | |
| 1 | LOADI | 2 | 3 | 0 | |
| 2 | OUTN | 3 | 3 | 0 | 3 |
| 3 | DEC | 4 | 2 | 0 | |
| 4 | JNZ | 2 | 2 | 0 | |
| 5 | OUTN | 3 | 2 | 0 | 2 |
| 6 | DEC | 4 | 1 | 0 | |
| 7 | JNZ | 2 | 1 | 0 | |
| 8 | OUTN | 3 | 1 | 0 | 1 |
| 9 | DEC | 4 | 0 | 1 | |
| 10 | JNZ | 7 | 0 | 1 | |
| 11 | HALT | 8 | 0 | 1 | |

Для початкового a=3 той самий результат дає C++:

```cpp
int a = 3;
while (a > 0) {
    std::cout << a << " ";
    --a;
}
```

Наш байткод перевіряє умову після тіла, тому для початкового нуля він
відрізнявся б від цього while: спочатку надрукував би 0, потім DEC дав би 255.
Коли JNZ спрацьовує, PC стає рівним 2. Додавати ще 3 не можна: тоді
процесор потрапить в операнд переходу замість OUTN.
Повний [вивід step/regs](checks/lab-04-trace-output.txt).

### Пошук на C++ та всередині ember

find lo hi byte шукає перший збіг у [lo, hi), тобто hi не входить у ділянку.
Допустимо 0 <= lo <= hi <= 4096; порожня ділянка дає not found.
Функція find_byte проходить адреси циклом for і повертає hi при промаху.
Команда друкує found at <адреса> або not found.

Програма-гість шукає 0x41 у восьми байтах [0x800, 0x808).
HLOW бере молодший байт H: для цієї ділянки він збігається з індексом 0..7.
Після INCH порівнюємо його з 8. Це перевірка кінця перед наступним LOAD.
Для іншого діапазону цей спосіб перевірки меж треба змінити.

```text
адреса  байти     інструкція
0000    28 00 08  LOADH H, 0800
0003    21 41     loop: LOADI B, 41
0005    29        LOAD A, [H]
0006    1A        CMP A, B
0007    31 15 00  JZ found
000A    2B        INCH
000B    2D        HLOW
000C    21 08     LOADI B, 8
000E    1A        CMP A, B
000F    31 18 00  JZ miss
0012    30 03 00  JMP loop
0015    2D        found: HLOW
0016    03        OUTN
0017    00        HALT
0018    20 FF     miss: LOADI A, 255
001A    03        OUTN
001B    00        HALT

0800    03 01 41 41 00 00 00 00  дані
```

```sh
./build/ember < checks/lab-04-search.txt
./build/ember < checks/lab-04-miss.txt
```

На наведених даних find друкує found at 2050, гість друкує 2 — індекс
першого збігу. Другий байт 0x41 вже не перевіряється. При промаху find
друкує not found, гість — 255. Це окрема ознака промаху, вона не збігається
з жодним допустимим індексом. H при промаху дорівнює 2056, дані за ним не читаються.
[Збіг](checks/lab-04-search-output.txt), [промах](checks/lab-04-miss-output.txt).
